# 雪酥移植记录

`xuesu_300` 是 SnowMux 面向雪酥·3（板型 ID `xuesu-300-std`）的构建环境。参考设备使用 ESP32-S3、16 MiB Flash、8 MiB PSRAM、300×400 墨水屏和三个实体键。日常操作和刷机入口见 [SnowMux README](../../README.zh-CN.md)；本页记录构建、发布和实机验收。实机已验证启动、SD 挂载、黑白刷新、TXT 和 EPUB 阅读。最新灰阶插图修正版通过构建和主机回归，仍需刷机复测。USB 磁盘、蓝牙重连和原厂阅读记录导入也待真机验收。

## 从源码构建

安装 [pioarduino Core 和 Python](../contributing/getting-started.md)，在包含本设备支持的检出根目录用 Bash 运行以下命令。Windows 可使用 Git Bash。干净检出时应用一次雪酥 SDK 补丁。

```bash
git submodule update --init --recursive
git -C freeink-sdk apply --check ../scripts/xuesu_freeink_sdk.patch
git -C freeink-sdk apply ../scripts/xuesu_freeink_sdk.patch
mkdir -p .pio
curl -fL https://xiaomoreader.top/XueSu_300OTA/firmware10033.bin -o .pio/xuesu-factory-1.3.3.bin
python3 scripts/prepare_xuesu_panel_lut.py .pio/xuesu-factory-1.3.3.bin
PYTHONUTF8=1 pio run -e xuesu_300
```

生成器校验原厂镜像的 SHA-256，并在 `.pio/xuesu-local-include/` 生成波形头文件。官网 1.3.3 镜像和参考设备的 OTA0 备份生成的头文件逐字节相同。原厂镜像、波形头文件、实机备份和编译产物都留在构建机的 `.pio/` 下。SDK 修改通过项目补丁随源码分发。

雪酥 GitHub Actions 构建会跑刷机网页、雪酥主机、XTC/XTCH、AirPage、网页文件页、字库、阅读界面（含微信读书）和 SDK 缓存回归。PlatformIO 平台、工具和 `xuesu_300` 库依赖单独缓存。手动在 `main` 构建固件后，会保存 `.cache/xuesu_300` 的编译对象，同工具链配置的后续构建和发版可以恢复。核对命中时同时看 Actions 的恢复日志和 `pio run` 的对象复用日志。

独立检出使用官网镜像和固定版本的 SDK 构建成功，应用镜像为 6,550,272 字节。esptool 校验了 ESP32-S3 镜像的校验和与哈希。该次构建复用了已安装的 PlatformIO 工具链，项目依赖重新安装。

构建产物 `.pio/build/xuesu_300/firmware.bin` 是应用镜像。实机安装流程会校验设备的真实分区表和原厂镜像，再写入 `ota_1`，读回后选择该槽启动。参考设备的 OTA1 从 `0x750000` 开始，容量为 `0x730000`。写入前保留各自设备的完整 Flash 备份。PlatformIO 的常规上传入口已关闭，合并产物 `firmware.factory.bin` 含开发板引导数据，写入参考设备会覆盖原厂数据。具体分区和既有试机记录见下文。

## 社区刷机站与发版

刷机站地址为 [clown145.github.io/snowmux](https://clown145.github.io/snowmux/)，使用 [GitHub Pages 的 GitHub Actions 发布来源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。其他项目仓库使用 `https://<owner>.github.io/<repo>/`，账号或组织站点仓库 `<owner>.github.io` 部署在同域名的根路径。

1. 新仓库在 **Settings → Pages → Source** 选 **GitHub Actions**。如果 `github-pages` 环境限制部署来源，在该环境的部署规则中允许标签 `xuesu-v*`。
2. [固件构建工作流](../../.github/workflows/xuesu-build.yml)在针对 `main` 提交 PR 时运行，也可手动运行。通过后可下载 `xuesu-firmware` 工件。若要预览刷机页，先在 `flasher/` 构建网页，再将工件解压到 `flasher/dist/`。
3. 在 **Releases** 发布形如 `xuesu-v0.1.1` 的版本，标签指向要构建的提交。[发版工作流](../../.github/workflows/xuesu-pages.yml)只构建一次带版本号的固件，把校验过的镜像、SHA-256 文件和许可附到 Release，再用同一工件部署网页和更新清单。只改刷机页时，可从默认分支手动运行发版工作流。它从当前更新清单对应的 Release 下载镜像，校验 SHA-256 后重新部署网页。[波形数据的许可说明](../../licenses/README.md#third-party-material)

刷机页提供 GitHub Release 附件的代理下载和直连入口。网页刷机先通过 `gh-proxy.com` 读取同一附件并核对 SHA-256，超时、下载失败或校验不符时改从 Pages 下载。

电脑上的 Chrome 或 Edge 使用 Web Serial。安卓 Chrome 使用 WebUSB，通过 `web-serial-polyfill` 连接雪酥的 CDC 串口（`303A:1001`），无需依赖 Android 17 的有线 Web Serial。手机需要支持 USB 主机模式和数据传输。用安卓 Chrome 打开 HTTPS 刷机页，连接并唤醒雪酥，点「连接设备」并允许 USB 访问。若选择备份，等读取完成后点「下载 Flash 备份」，在下载列表确认文件已保存。iPhone 和 iPad 可下载固件。

两种连接都检查 ESP32-S3 安全状态、Flash 容量和雪酥·3 分区表。网页按 ESP-IDF 启动记录的序号和 CRC 决定写入槽位，原厂各版本与社区固件使用同一流程。从 OTA0 启动时写入 OTA1，从 OTA1 启动时写入 OTA0，读回校验成功后才切换启动槽。首次安装前可保存 16 MiB Flash 备份，后续更新可能覆盖原厂应用槽。

从设备内「恢复原厂固件」返回 OTA0 的实机记录为 `0xF000: seq=3, VALID` 和 `0x10000: seq=2, UNDEFINED`。网页写入并校验 OTA1 后，在 `0x10000` 写 `seq=4`。单元测试使用这组实机记录，并覆盖写入前启动记录变化和新镜像读回失败。

写入校验完成或主动断开设备时，网页清除 ESP32-S3 的强制下载标志，再把 RTS 拉有效 100 ms 后释放。esptool-js 0.7.1 默认只释放已空闲的 RTS，会让雪酥留在刷机模式。用同一 JavaScript 刷机库通过 COM12 验证：旧流程结束后刷机程序仍回应，修正后日志显示 `USB_UART_CHIP_RESET`、`SPI_FAST_FLASH_BOOT`，固件自行启动。测试设备未插 SD 卡，启动后进入预期的 SD 卡错误界面；测试未写入 Flash。

浏览器复测可先连接再点「断开设备」，保持 USB 连接并确认设备自行启动。用旧版原厂固件复测首次安装，确认网页显示另一槽，刷机后可启动且原槽内容保留。再次更新时核对页面显示的目标槽和刷后启动。安卓实机还应验证 USB 授权、手动保存备份和拔线后重新连接。

用模拟 WebUSB 接口桥接 COM12，验证了安卓路径的机型检查、完整 16 MiB Flash 读取和重启。该轮未写入 Flash。模拟页面另验证了首次安装的备份下载步骤，以及下载固件时拔线会阻止写入。安卓 Chrome 的授权和 USB 传输仍需手机实测。

雪酥启动时若无法读取 SD 卡，会显示插卡提示。插好卡后，长按确认键至少 3 秒并松开，设备会重启并重新挂载 SD 卡。验收时先无卡启动，检查短按不会重启，再插卡并长按，确认进入首页。开机时已经按住的确认键须先松开，再重新长按。

本地预览从 `flasher/` 运行 `npm ci`、`npm test`、`npm run build` 和 `python -m http.server 8765 --directory dist`，然后打开 `http://localhost:8765/`。需要打包固件时，用 `XUESU_RELEASE_TAG=xuesu-v0.1.1 pio run -e xuesu_300` 构建测试版本，再以相同标签运行 `python scripts/package_xuesu_pages.py`，具体参数见 `--help`。

### 更新查询接口

`GET /api/v1/firmware/latest.json` 相对于站点根路径，项目站的完整地址为 `https://<owner>.github.io/<repo>/api/v1/firmware/latest.json`。发版时静态清单和它指向的镜像一起部署。网页也从该接口获取当前版本。

| 字段 | 含义 |
| --- | --- |
| `schema` | 接口格式版本，当前为 `1`。 |
| `board`, `target_partition` | 板型 `xuesu-300-std`，从 OTA0 启动时的目标槽 `ota_1`。网页根据设备的启动槽决定写入位置。 |
| `tag_name`, `release_tag`, `commit` | 社区版本号（如 `0.1.0`）、GitHub 标签（如 `xuesu-v0.1.0`）和源码提交。 |
| `assets[0]` | 逻辑文件名 `firmware.bin`、字节数 `size`、HTTPS 下载地址 `browser_download_url` 和 `sha256:` 前缀的 `digest`。网页串口读回使用该条目的 `md5`。 |

### 设备内更新

没有「检查更新」入口的旧版须先通过 USB 刷入支持设备内更新的版本。此后从「设置 → 系统 → 检查更新」连接 Wi-Fi，设备从 SnowMux 刷机站读取更新清单。支持加速的固件会直接通过 HTTPS 请求 `gh-proxy.com` 上的 GitHub Release 附件，无需为设备设置代理。连接、传输或校验失败时，设备从清单中的 Pages 地址重新开始写入。两条路径均验证 TLS 证书，并用清单 URL 中的 SHA-256、镜像大小、ESP32-S3 芯片 ID 和雪酥板型标记验证镜像。已有固件仍可用同一清单和 Pages 地址升级。

更新器只写两个应用槽中空闲的一个，并在完整验证后切换启动槽。第一次从 OTA1 更新会覆盖 OTA0 中的原厂固件，确认框会标明写入目标。后续更新交替使用 OTA0 和 OTA1。下载中断时设备仍从当前槽启动，再试会重新下载。

同一菜单中的「恢复原厂固件」读取[官方刷机页](https://xiaomoreader.top/tools/XueSuFlash.html)使用的[更新清单](https://xiaomoreader.top/XueBingOTA/version.json)，选取 `xuesu-300-std` 当前发布版本并显示版本号。确认后通过 HTTPS 下载，校验清单大小、ESP32-S3 芯片 ID 和 ESP 应用镜像，再从写入的槽启动。恢复范围为原厂应用和 OTA 启动选择。要恢复整片 Flash 的原始状态，可用首次安装保存的本机完整备份经 USB 串口恢复。

真机验收时先测试 OTA1 到 OTA0，再用更高版本验证 OTA0 到 OTA1。另测试下载中断、镜像校验失败、两个槽上的原厂恢复和 USB 备份恢复。原厂引导器在新应用启动失败时的自动回滚行为待实测。

## 墨水屏初始化

[雪酥板卡参数](../../include/boards/Xuesu300Board.h)记录了 1.3.3 的 SPI 引脚、原生 400×300 分辨率和 `0x4209278C` 的 10 组寄存器写入。原厂在 `0x4202012C` 配置 20 MHz SPI（Mode 0、MSB first），经 `0x4215A284` 传入 10 ms 复位脉宽。`0x42092278` 的复位流程先拉高 10 ms，再拉低 10 ms，最后拉高并等待至少 10 ms。BUSY 为低有效，`0x42092658` 配置的等待超时为 10 秒。

- `0x61` 的四个数据字节为 `01 90 01 2C`，与构造函数里的 400×300 一致。写显存路径用 `0x10` 和 `0x13`，一张全屏 1-bit 位图为 15,000 字节。局刷窗口从 `0x90` 设置（`0x420926C4`）。
- 刷新路径 `0x42092948` 先写 `50 D7`，再写 `17 A5`。[UC8276C 手册](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=21)把 `17 A5` 定义为自动上电、刷新和关电。
- `0x42092898` 分别向 `0x20` 至 `0x24` 写入 42 字节波形数据。波形字节留在本地原厂镜像里。

屏幕构造函数里的枚举值 `0x25` 对应 [GxEPD2 的 GDEW042T2](https://github.com/ZinggJM/GxEPD2/blob/master/src/GxEPD2.h)。同名面板使用 UC8176，其手册只定义单字节 `0x00`，也未列出 `0x17`。见 [UC8176C 命令表](https://files.waveshare.com/upload/8/88/UC8176.pdf)。原厂实际写入 `00 3B 4A` 和 `17 A5`，这两处与 [UC8276C 命令表](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=7)更接近。

离线比较时，UC8279 系列也曾是候选。它与雪酥有部分相同的命令，FreeInk 的 UC8279d 适配也写入 42 字节黑白波形。实机读到的 `CHIP_REV=0x07` 和空闲状态 `0x13` 与 UC8276C 手册吻合，因此后续以 **UC8276C** 为驱动适配基线。见 [UC8276C 版本与状态寄存器](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=33)及 [FreeInk UC8279d 记录](../../freeink-sdk/libs/display/FreeInkDisplay/src/lut/Uc8279X3Luts.h)。

公开 UC8276C 命令表未列出 `E1 02`，`0x20` 规定 56 个数据字节，SPI 写入周期至少 100 ns（最高 10 MHz）。原厂固件的对应路径发 42 字节，配置时钟 20 MHz。诊断保留原厂配置值，首个显示测试应按面板规格使用较低频率，并实测刷屏与 BUSY 时序。见 [UC8276C 命令表](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=7)和[交流特性](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=59)。

## 早期接入计划

1. 通过 USB 只读识别实机，记录芯片、安全配置和分区。确认可恢复的原厂备份，再验证板级接线。
2. 按 [FreeInk SDK 新设备流程](../../freeink-sdk/README.md#adding-a-new-device)增加雪酥 `BoardProfile` 和独立的 PlatformIO 环境。复用 `SdmmcBlockDevice` 的四位总线和匹配控制器的屏幕驱动。现有 S3 环境提供构建参考，雪酥的引脚、分区和电源设置来自本机证据。
3. 首个真机验收是串口启动日志、黑白测试图、按键和 SD 卡读写。随后验证中文 TXT/EPUB、保存进度、Wi-Fi 传书以及电池供电下的休眠唤醒。
4. 基础阅读和联网稳定后接入现有的[微信读书模块](../../src/activities/apps/weread/README.md)，按扫码登录、书架、离线 EPUB、手动同步位置的顺序验证。先核对设备端的 TLS 证书验证策略。

## 诊断构建

`xuesu_300_probe` 单独构建 ESP32-S3 N16R8 的串口诊断。它读取芯片型号、物理 Flash 容量、已初始化的 PSRAM 容量和设备当前分区表。串口连上后会打印一次，发送 `?` 可重读。发送 `p` 可打印板卡参数、参考样机的屏幕芯片修订号和原厂寄存器表。该命令只写串口。

`partitions_xuesu_300.csv` 复现了实机分区。生成的 `partitions.bin` 与原厂备份 `0x8000` 起的 `0xC00` 字节完全一致，诊断应用的构建地址为 `0x20000`。配置保留上传保护。PlatformIO 合并产物 `firmware.factory.bin` 仍含开发板 bootloader 和 `0xE000` 的 `boot_app0.bin`，后者会覆盖原厂 NVS 末尾及部分 OTA 元数据。测试使用单独的应用镜像，整包产物仅供构建检查。

```powershell
$env:PLATFORMIO_CORE_DIR = Join-Path (Get-Location).Path '.pio\.platformio'
& .\.venv\Scripts\pio.exe project config --lint
& .\.venv\Scripts\python.exe scripts/patch_pioarduino_cache.py --prepare-platform
& .\.venv\Scripts\pio.exe run -e xuesu_300_probe
```

开发分支为 `codex/xuesu-300-port`。原厂镜像、IDA 数据库和本地工具缓存放在 Git 忽略的 `.pio/` 下。发布时沿用项目 [LICENSE](../../LICENSE) 和[第三方许可说明](../../licenses/README.md)。

## 首次真机识别（2026-11-10）

Windows 在 `COM12` 枚举出原生 USB Serial/JTAG（`303A:1001`）。esptool 5.6.0 通过 ROM 下载模式确认 ESP32-S3 v0.2、双核、片内 8 MiB PSRAM，以及 16 MiB Quad SPI Flash（JEDEC `C8 40 18`）。Secure Boot 和 Flash 加密均关闭。

首次全片读取约到 5.75 MiB 时 USB 串口从系统消失。重新接入后按 1 MiB 分段读取，每段通过传输摘要校验。拼接得到 16,777,216 字节，`esptool verify-flash` 的整片设备摘要校验通过。备份与 `SHA256SUMS.txt` 保存在 Git 忽略的 `.pio/xuesu-device-backups/2026-11-10/`。

原厂分区表位于 `0x8000`，ESP-IDF 表内 MD5 校验通过。此台样机 `ota_0` 有有效应用，`ota_1` 无应用头，`otadata` 无有效 OTA 选择记录。

| 分区 | 地址 | 大小 |
| --- | --- | --- |
| `nvs` | `0x9000` | `0x6000` |
| `otadata` | `0xF000` | `0x2000` |
| `ota_0` | `0x20000` | `0x730000` |
| `ota_1` | `0x750000` | `0x730000` |
| `spiffs` | `0xE80000` | `0x180000` |

实机 `ota_0` 镜像不同于公开 1.3.3，镜像校验和及 SHA-256 均有效。`0x4202DD92` 的屏幕构造调用和 `0x4202CFB2` 的 SPI 初始化复核了原先的六个 GPIO。`0x42094B32` 的 10 组初始化写入和 `0x42094CCC` 的自动刷新命令与公开镜像对应片段逐字节相同。`0x42094C1C` 仍向五个波形寄存器各写 42 字节。

用 `esptool load-ram` 运行临时半双工 SPI 探针。GPIO1 在面板复位后为高电平；GPIO5 切换为输入回读，分别使用内部上拉和下拉，各读一次，均得到 `0x70 = 00 07 FF FF FF` 和 `0x71 = 13`。`0x70` 的第二字节对应 UC8276C 固定芯片修订号 `0x07`，`0x71` 的最低位与实测 BUSY 空闲电平一致。探测结束后执行硬复位。随后 Windows 未枚举 COM12，原厂界面的恢复未从电脑端观察到。面板料号及独立供电时序仍待核对。

## 黑白全刷测试（2026-11-10）

通过 `esptool load-ram` 在实机运行一次性黑白探针。以 GPIO5 半双工回读 `CHIP_REV=0x07` 和复位后 `0x71=0x13`，确认后发送实机原厂初始化表。全刷波形来自实机 `ota_0` 中 `0x42094DC8` 的调用参数，按 `0x20` 至 `0x24` 各发送 42 字节，保存在本地忽略目录。位图以每平面 15,000 字节送入 `0x10` 和 `0x13`，由 `17 A5` 触发自动刷新。使用低速 GPIO 模拟 SPI。

BUSY_N 从高转低，约 1.12 秒后回到高。关电后 `0x71=0x1B`，最低三位为 `011`，对应空闲和关电状态。测试图为 400×300 的 4×4 黑白棋盘格，含黑边和方向标记。实机照片显示 16 个格子完整，方向标记在照片左下，符合竖屏显示。用户先报告画面疑似有残影，随后用棋盘格作旧帧、全白作新帧再次全刷。BUSY_N 低电平约 1.12 秒，关电后状态仍为 `0x1B`，用户目视确认全白且看不到棋盘格。

## 按键和 TXT 试机（2026-11-10）

在 RAM 探针中分别短按上一页、下一页和确认。每个键松开后都恢复空闲。上一页 GPIO46 和下一页 GPIO45 为高有效，确认 GPIO17 为低有效。SD 卡供电控制 GPIO42 拉高，四位 SDMMC 使用 CLK=38、CMD=39、D0=47、D1=48、D2=41、D3=40。用户在原厂系统打开了卡上的书并成功翻页。

`xuesu_300_txt_test` 是独立的板卡试机程序。它从 SD 卡扫描 TXT，复用 CrossMux 的编码检测和 GBK 映射表，支持 UTF-8 和 GBK。书架上短按确认打开，上下页键可在第一本和最后一本之间循环。阅读中用上下页键翻页，短按确认返回。每次更新使用黑白全刷。试机版用只读方式打开书籍，最多列出 64 本，扫描卡根目录及向下三层目录，阅读进度保存在内存里。

书名和正文优先使用 U8g2 的文泉驿 14 点阵 `gb2312` 字库，缺字时查找 GNU Unifont Japanese 第三子集。刷入 OTA1 后，用户在同一 GBK TXT 首页确认「瀬」和「喵」均显示正常。用 Python 编解码器枚举双字节码位后，以固件使用的 U8g2 字形宽度检查覆盖。两套字库合计覆盖 GB2312 的 7,444 / 7,445 个码位（缺 U+2015）和 GBK 的 8,807 / 21,791 个码位。缺失的字符仍显示问号。[U8g2 字库源文件](https://github.com/olikraus/U8g2_Arduino/blob/1558c1260d6485d8b637f64ab7eb75fa50c23cc1/src/clib/u8g2_fonts.c)

试机版使用固件内置字库。原厂备份中可见外部字体选择菜单、`.bin` 和 TrueType 加载分支，官网雪酥 1.3.3 更新说明列有 TTF 修复。该样机尚未做原厂字体导入实测。CrossMux 的应用层已有 SD 字体加载和选择菜单，启用 PSRAM 的目标可从 `/fonts/` 或 `/.fonts/` 加载 `.ttf`、`.otf`、`.ttc`，也可使用 `.cpfont` 位图字体。[原厂 OTA 清单](https://xiaomoreader.top/XueBingOTA/version.json) · [CrossMux 字体说明](../sd-card-fonts.md)

完成[源码构建](#从源码构建)中的波形生成步骤后，运行 `pio run -e xuesu_300_txt_test` 构建历史试机目标。

试机应用为 `.pio/build/xuesu_300_txt_test/firmware.bin`。首次写入前用 esptool 校验原厂 `ota_0`、原厂 OTA 选择记录和 `ota_1` 的待写范围，再将应用单独写入 `0x750000`。写入摘要校验通过后，将 `seq=2` 的选择记录写入原厂空白的第二个 OTA 元数据扇区 `0x10000`。串口确认运行分区为 `ota_1`、SD 卡挂载成功、发现 53 个 TXT，墨水屏完成刷新。试机目标跳过 Arduino 默认 NVS 初始化。

该参考设备回退时，恢复试机前备份的 `0x10000` 扇区原始 4,096 字节并复位。其他设备先核对自己的实际分区布局和 OTA 选择记录，使用自己的备份。

## 雪酥热点配网

从「设置 → 连接 → 热点配网」启动临时热点。雪酥默认显示加入 `CrossMux-Setup-*` 的 WPA 二维码，按任一上下键可切换到临时密码。加入热点后打开屏幕显示的 HTTP 地址。网页复用 CrossMux 的共享样式和标志，扫描附近 2.4 GHz 网络，也可以手动输入隐藏网络的名称。密码从网页提交，只在设备连上路由器并取得 IP 后写入 CrossMux 的 SD 卡凭据文件。

配网服务只绑定热点接口，临时密码每次重新生成，同时允许一个热点客户端。设备在 AP+STA 模式下验证连接，失败时保留热点以便重试，成功后关闭热点。应用发起配网时将已连接的 STA 交给应用。由设置进入时在保存完成后关闭无线电，联网功能下次会自动使用已保存的网络。长按确认可以退出配网。

## 黑白快刷

雪酥使用实机原厂 `ota_0` 的两套黑白波形。`0x42094DC8` 使用全刷波形，`0x42095500` 装载差分波形，均按 `0x20` 至 `0x24` 各发送 42 字节。构建前从同一份校验过的本地备份提取，波形数据留在忽略目录。

最初的试机版用九字节 `0x90` 限定窗口，只发送变化区域的两份黑白显存平面，`PT_SCAN=0`。记录总线验证通过，但实机首次局刷就出现明显缺块或旧内容。该版镜像为 6,548,176 字节，启动时串口测得全刷 1,126 ms，376×300 窗口刷新 525 ms。BUSY 返回只表示控制器完成该指令。[UC8276 寄存器手册](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=37)

快刷修正版在每次刷新时上传完整的旧帧和新帧，各 15,000 字节。普通操作使用原厂短波形，画面相同就跳过。原厂差分激活路径 `0x42095544` 到 `0x42094D14` 未设置局刷窗口。首次刷新、应用请求清屏和超时后的下一帧使用全刷。阅读器的清残影频率沿用原有设置。

桌面记录总线验证了连续三次只改少量像素时旧、新平面内容及方向，波形选择，相同帧跳过，定期清屏和三种 BUSY 超时后的恢复。快刷修正版 `xuesu_300` 构建通过，镜像为 6,547,632 字节。

OTA1 写入和启动选择校验通过。串口收到完整的 15,000 字节帧缓冲，启动全刷耗时 1,126 ms，差分快刷耗时 524 ms。计时从激活命令到面板完成关电，不含发送帧数据。该版实体屏上的旧内容大多能擦除，新内容仍大面积缺失。

复核原厂差分波形装载调用。装载器 `0x42094D30` 给 `0x23` 取调用者栈的 `SP+4`，给 `0x24` 取 `SP+12`。此前提取脚本将两项交换，导致白到黑使用了保持波形。现按实际寄存器顺序提取。全刷表的对应两项字节相同，生成的全刷波形相同。记录总线新增按寄存器检查首段驱动方向的断言，覆盖 WW、KW、WK、KK 四种转换。[UC8276C 波形寄存器定义](https://v4.cecdn.yun300.cn/100001_1909185148/UC8276.pdf#page=24)

波形顺序修正版构建及 OTA1 写入校验通过，启动返回完整的 15,000 字节帧缓冲。启动全刷 1,126 ms，差分快刷 524 ms。继续采用完整的新旧帧传输。用户实机确认快刷正常，新出现的内容显示完整。

## 电池电量与充电状态

实机原厂 OTA0 的初始化函数 `0x42025050` 配置 ADC2_CH3（GPIO14）为 2.5 dB，并把 GPIO16 配置为上拉输入。充电状态低有效。采样函数 `0x42025108` 对 16 次 ADC 采样排序，去掉两端各 2 个，分压换算为 4.3 倍。电量按 `0x3C187838` 的 13 个电压点插值，范围为 3,300 mV 的 0% 到 4,200 mV 的 100%。[乐鑫引脚与 ADC 通道对照](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/schematic-checklist.html#adc)

CrossMux 通过 FreeInk 的电池驱动采集经芯片校准的毫伏值。主任务在启动和之后每 15 秒采样，发布给 UI。有效读数变化会更新菜单上的电量，阅读正文时随下一次翻页更新。ADC2 与 Wi-Fi 共享，读数失败或超出有效范围时保留上次有效电量。充电闪电图标使用 GPIO16 的状态，充满停止充电后熄灭。初版使用原厂的标称曲线，未引入原厂保存的单机满电校正值。[ESP-IDF ADC 单次采样说明](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-reference/peripherals/adc_oneshot.html)

电源回归测试覆盖板卡配置的引脚、充电状态极性、曲线插值、去除离群样本、采样间隔和 ADC 失败恢复。FreeInk 电池及输入主机测试通过。

雪酥构建通过，6,435,728 字节镜像写入 OTA1 并校验成功。USB 接线状态下，启动读到 4,190 mV（99%），后续连续两次读到 4,183 mV（98%），首页右下角显示 98%。三次采样的 GPIO16 均未报告充电，充电中图标亮起仍待实机核对。

### 满电校准

「设置 → 系统 → 满电校准」仅在雪酥显示。充满后等充电红灯熄灭，保持 USB 连接，再确认校准。主任务取 10 组去掉离群值的电压读数，每组间隔约 50 ms。检测到充电中、读取失败或读数偏离 4,100–4,300 mV 时，界面提示原因。

CrossMux 将平均值保存到 SD 卡 `/.crosspoint/settings.json` 的 `xuesuBatteryFullMv`，保存成功后应用，启动时重新加载。计算电量前，按「实测电压 × 4,200 ÷ 满电基准」换算电压，沿用原有 13 个插值点。没有有效校准值时使用原始读数。

主机测试覆盖 4,183 mV 从 98% 校正为 100%、校准值重新应用、无效基准回退和充电中拒绝采样。6,437,488 字节校准版镜像写入 OTA1 并通过校验，设备已启动。

RTC 记录改用无构造的字段，编译期断言禁止引入会在启动时初始化的成员。新标记使旧版本的记录失效。已检查目标文件无启动初始化入口，链接产物的 `.rtc_noinit` 为 `NOBITS`。回归覆盖休眠默认设为手绘时，在待机里切到报刊排印后的五次分钟刷新和温湿度重采样，也覆盖旧记录失效。21 项雪酥主机回归通过。

雪酥版镜像为 6,417,008 字节。OTA1 写入与读回校验通过，原厂 OTA0 和分区表摘要一致，真机抓屏确认重启到 INX 首页。尚未抓到修复后的深睡定时刷新。复测时在「待机显示」选报刊排印，等待约 35 秒进入深睡，再跨两个分钟边界检查时间更新和表盘样式，短按确认应回到报刊排印。

### 插图、USB 传书与原厂书库兼容

- 书内插图和图片查看器在黑白面板上用有序抖动保留中间色调。图片查看器跳过用不上的灰阶遍历。雪酥为 PNG 两行解码窗口放宽到 4096 像素宽的 RGBA 输入，优先用 PSRAM 分配解码器。真机验收用同一张包含浅色渐变和透明边缘的图片，分别从 EPUB 和文件管理器打开，检查细节及翻页残影。原厂灰阶波形待移植。
- 「文件传输 → USB 磁盘」会停止蓝牙并卸载本机 SD 文件系统，再把 SD 卡作为 U 盘交给电脑。传完先在系统中弹出，设备随后返回首页并重新挂载。真机验收复制一本书，从电脑弹出后核对文件大小并打开阅读。
- 文件列表与书库支持 `.mobi`、`.azw3` 和 `.docx`。首次打开会在 `/.crosspoint` 的每书缓存生成 EPUB，原文件路径继续作为书籍身份。MOBI/KF8 使用 PSRAM，源文件上限 4 MiB，支持未加密的流式书籍。DOCX 提取正文和内嵌 JPEG、PNG、GIF 后重排，并保留 Word 的不间断连字符。已有 DOCX 下次打开时重建转换缓存并沿用阅读进度。DOCX 主 XML 上限 32 MiB，最多处理 64 个图像关系，单张内嵌图片上限 8 MiB。Word 原版式、页眉页脚和复杂表格布局待支持。可用含目录的 MOBI、含 CJK 的 AZW3 和带嵌入图的 DOCX 验证首次打开、再次打开、翻页和进度保存。
- 「设置 → 通用 → 导入原厂最近阅读」读取 `/.ereader/recent_books.json` 版本 1，只追加 SD 卡上仍存在且可打开的书。没有 CrossMux 进度的书首次打开时按原厂记录的百分比定位。原厂的精确位置、累计统计、字体、壁纸及设置暂未迁移。用一份有原厂阅读历史的 SD 卡验证重复导入和已读书的进度优先级。
- 原生 SDMMC 读写出错时显示备份提示。15 秒内三次成功传输各耗时至少 150 毫秒时显示慢卡提示，每次启动同类提示最多一次。用独立测试卡复测，串口的 `SDMMC transfer failed` 可对应核查读写故障。
- BLE 配对列表和 NimBLE 密钥各存一份带校验的雪酥专用 SD 文件，复用暂存与替换流程。用一只 BLE HID 翻页器验证配对、重启与深睡后重连、实际翻页和取消配对后重新启动。以前丢失密钥的设备需要重新配对一次。

`xuesu_300` 构建成功，OTA1 应用镜像为 6,546,256 字节，通过 ESP32-S3 镜像校验。静态 RAM 129,644 / 327,680 字节，Flash 6,541,023 / 7,536,640 字节。57 项主机回归通过，另外检查了五本 MOBI/KF8 样书的资源清单、DOCX 分块解析与内嵌 PNG、原厂最近阅读去重及百分比解析。该镜像尚未刷入设备，USB、墨水屏和 BLE 翻页器验收待真机完成。

### UC8276C 原生四阶灰度与 XMPIC

实机 OTA0 的灰阶入口 `0x420955C4` 调用 `0x42094C1C`，用 `0x4215C8BC` 生成两组 `0x20` 至 `0x24` 波形，并由 `0x4215C91C` 写出两张选择平面。官网 1.3.3 镜像中对应的生成和编码逻辑一致。用本机校验过的 OTA0 运行 `scripts/prepare_xuesu_panel_lut.py`，重新生成带两组灰阶波形的本地头文件，再构建 `xuesu_300`。[原厂 1.3.3 镜像](https://xiaomoreader.top/XueSu_300OTA/firmware10033.bin)

阅读设置的「图片 → 显示」和独立图片查看器使用全帧四阶灰度。驱动先建立已知白底，第一趟输出黑、浅灰和白，有深灰像素时再使用原厂第二趟波形。返回黑白画面用全刷恢复快刷基准。两张选择平面共 30,000 字节，单次刷新期间存于 PSRAM，每行用 50 字节栈缓冲发送。低内存时直接显示黑白预备帧。普通文字页走黑白路径，反色或有自定义阅读背景的书页用黑白抖动。

官方 XMPIC 导出是无头的 1 bpp 位图。雪酥规格为 300×400，按从上到下的行序存储，每行 38 字节，最高位对应最左像素，1 为黑。文件浏览器识别大小写扩展名，校验文件为 15,200 字节后，逐行生成带正确调色板的临时 BMP，沿用现有图片查看和休眠封面功能。字节数不符或读取不完整时显示图片错误。[原厂壁纸工具](https://xiaomoreader.top/tools/XueBingWallpaper.html)

`xuesu_300` 构建通过，OTA1 应用镜像为 6,548,880 字节，ESP32-S3 校验和和镜像哈希有效。静态 RAM 129,660 / 327,680 字节，Flash 6,543,639 / 7,536,640 字节。59 项主机回归通过，涵盖实驱动的 LUT 选择、平面极性和旋转、灰阶到黑白、低内存和 BUSY 超时，以及 XMPIC 的文件入口、损坏文件和休眠封面。另执行了官网 XMPIC 导出函数，生成与固件测试相同的四个角位。全仓 CI 停在其他文件的格式检查，X3/X4 默认目标停在 Windows 链接脚本生成命令过长，原生灰阶模拟器套件仍受 Windows POSIX 兼容限制。

已通过 COM12 写入并选中 OTA1。应用镜像和启动记录通过独立读回摘要校验，分区表和原厂 OTA0 摘要与备份一致。重启后串口确认 SD 挂载和 SD 字体加载，完整帧缓冲显示 INX 最近阅读首页。灰阶色差、刷新残影与 XMPIC 文件打开待按下文实测。

真机验收使用一张同时包含纯黑、深灰、浅灰和白色的 PNG，分别在图片查看器和 EPUB 正文打开，拍摄实体屏确认四块色调、方向和边缘。连续翻过两张灰阶图，再返回纯文字页和菜单，检查黑白快刷恢复、刷新闪烁与残影。用官方工具导出的 300×400 XMPIC 检查四角方向、文件列表的相邻图片切换和休眠封面。

### EPUB 灰阶插图空白

真机上「图片 → 显示」时插图区域空白，同一页切到「黑白」可见。雪酥的阅读器开启了黑白预备帧抖动，`DirectPixelWriter` 也据此跳过灰阶写入，导致全帧灰阶的两张位平面在插图区域保持白色。像素写入器现在区分完整的灰阶位平面和文字抗锯齿叠加，完整灰阶位平面始终写入插图像素。

回归测试用白底复现旧实现的空白，修复后确认四个灰度值在两张位平面的编码正确。测试同时覆盖黑白图像模式下跳过文字抗锯齿叠加的行为。真机可用出现问题的同一页切回「图片 → 显示」验证。

`xuesu_300` 构建通过，修正版 OTA1 镜像为 6,548,864 字节，ESP32-S3 镜像校验和与哈希有效。55 项主机测试通过。设备暂未连接，修正版尚未刷入。

### 阅读差分灰度

「文字设置 → 样式 → 灰度文字」默认关闭，雪酥用独立的 `grayReadingText` 设置保存。开启后，浅色 EPUB、TXT 阅读页的字形覆盖度进入两张绝对灰度位平面。反色页走黑白，插图保持所选的黑白或灰度模式，自定义背景作为两张位平面的共同黑白底图。

原厂官网 1.3.3 的 `displayGrayDiff`（`0x42093240`）使用 `0x4215A2FC` 比较新旧像素，复用两组灰度波形。第一趟的面板选择码按黑、深灰、浅灰、白依次为 `10`、`11`、`00`、`01`，未变化像素为 `11`。仅有像素变成深灰时提交第二趟。SnowMux 保留两张已提交位平面共 30,000 字节于 PSRAM，与现有的 30,000 字节暂存缓冲互换。首次进入、手动清屏和周期清屏先建立白色基准。切到黑白、取消刷新或刷新超时时丢弃灰度历史。 [原厂 1.3.3 镜像](https://xiaomoreader.top/XueSu_300OTA/firmware10033.bin)

实机验收可在同一本 EPUB 和 TXT 上分别关闭和开启开关，连续前翻和回翻，覆盖至少一个清屏周期。串口用 `Rendered page in` 记录整页耗时，用 `Refresh differential`、`Refresh gray differential` 和 `Refresh full` 区分快刷、灰度差分和清屏。观察屏幕翻页过程中的全屏闪动，以及旧字在空白处的残影。退出后应恢复黑白菜单。

2026-11-12 实机试机版写入空闲 OTA0，应用和启动记录均通过独立读回摘要校验，保留原 OTA1。启动后串口确认 SD 卡挂载。普通页从正文绘制开始计时，EPUB 关为 736–748 ms（3 页），开为 1,541–1,561 ms（2 页）。TXT 开为 1,573–1,630 ms（5 页），关的样本待采集。开启后的首个带清屏样本为 2,836–2,849 ms。普通灰度页两次波形各占 543–544 ms，两次完成相隔约 0.70 秒。现场观察到正文分两段显现，短时显示反馈正常。长时间连续阅读的残影待验。

### XTC/XTCH 阅读和内置中文字库

XTC/XTCH 按当前页的尺寸读取和绘制，并校验页头与页表的宽高一致。超出屏幕的页面按原比例缩小并居中，直接从已解码的页面取样，不分配缩放缓冲。雪酥的 XTCH 正文使用整帧四阶灰度，刷新失败时重画黑白抖动页。「XTC 状态栏」的顶部、底部和隐藏设置同时适用于 XTCH。真机可打开包含 300×400 和 480×800 页面、四角都有标记的样书，核对翻页、四角、四级灰度和状态栏位置。

14、16、18 pt 中文界面字库增加当前翻译缺少的 17 个字。字形覆盖测试检查了新增字形，原有字形的像素和度量通过了指纹比对。

### 文件传输与其他灰阶入口

USB 主机直接读写 SD 扇区，固件无法通过文件名识别改动。因此 USB 磁盘模式在卸载 SD 前写入既有索引更新标记，包括只浏览的会话。验收时先打开书库建立索引，再通过 USB 新增和删除各一本书，安全弹出后重新打开书库，核对两项变动和原有书目的最近添加次序。

AirPage 收到灰阶图片时使用两张全帧选择平面，刷新失败时尝试提交黑白抖动图。老黄历只在时间有效的非反色沉浸模式下使用四阶灰度，文字根据字形覆盖度生成灰阶，宜忌框的反白文字也使用同一套覆盖度。老黄历复用绘图器的分块黑白缓冲保留预备帧。实机可推送四色样图，检查四种色调和退出后黑白菜单，再查看老黄历宜忌框及小字的边缘。

网页从现有下载入口读取 XMPIC，在浏览器解码为 300×400 图片。预览窗口的下载链接仍指向原文件。可在中英文网页分别点击一张对角带黑色标记的 XMPIC 检查方向，再打开一张截断文件检查错误提示。
